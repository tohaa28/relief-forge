# Обязательный протокол фиксации каждой разработки

**Вступает в силу с этой документационной ревизии.** Код/релиз без сохранения причин изменений, альтернатив, неудачных попыток и проверок считается незавершённой передачей проекта. Не переписывать старые записи, даже если следующая гипотеза оказалась правильной.

## 0. Перед началом работы

1. Прочитать \`AGENTS.md\` → \`docs/NEXT_CHAT_START.md\` → \`docs/history/FAILURE_REGISTER.md\` → \`docs/history/METHODS_AND_DECISIONS.md\` → текущий \`HANDOFF.md\` и последний \`docs/DEVELOPMENT_LOG.md\`.
2. Проверить реальный GitHub \`main\`, последний PR (state/merged status), latest workflow build+deploy, текущее имя/version и live page. Никаких предположений о старом состоянии от прошлого чата.
3. Создать feature branch из **наблюдённого SHA**. Не перезаписывать main напрямую, если возможен проверяемый PR.
4. Сразу записать изменяемые модули и инварианты: точки только M/L/C/Q, Undo, AFTER ≡ export, реальные цвета/holes, изоляция файлов пользователя.
5. Сохранить checkpoint SHA до первой правки (а для пользовательской GUI-правки — наблюдаемые снимки и их версию).

## 1. Каждое изменение (выполненное, частичное или неудачное)

В \`docs/DEVELOPMENT_LOG.md\` добавлять новый раздел **в порядке времени**:
\`\`\`markdown
## YYYY-MM-DD HH:MM ±TZ · [version/branch] — название
- Запрос: точная пользовательская проблема и ожидаемый результат
- Входные данные: формат, имя, размер, хеш (по возможности), где сохранены
- Версия до изменения: branch, SHA, доступный Pages URL
- Диагноз: наблюдаемое, воспроизведение, код и измеренные числа
- Гипотезы: отдельно от доказанных причин
- Попытка #1: файл/функция, конкретная идея, тест/ошибка и почему отказались
- Попытка #2…: аналогично, включая изменения, которые были откатаны
- Принятое решение: алгоритм, параметры и выбранные ограничения
- Изменённые файлы: конкретные пути и назначение каждой правки
- Новые/исправленные тесты: что они доказывают, исходный FAIL и последующий PASS
- Безопасность данных: приватные EPS, лицензии, Undo, геометрия, CMYK
- CI: run URL, event PR/main, numbers JS/Rust/WASM, job states
- Git: PR URL, merged SHA или «НЕ ОПУБЛИКОВАНО»
- Browser smoke: браузер, экран, реальный EPS/PDF, статус либо «не проверено»
- Что осталось/risks/следующее действие:
\`\`\`

Одновременно дописывать **одну или более JSONL-записей** в \`logs/actions.jsonl\`:
\`\`\`json
{"at":"YYYY-MM-DDTHH:MM:SS+TZ","action":"short-kebab-id","status":"investigating|failed|implemented|ci_pass|ci_fail|merged|deployed|user_verified","base_sha":"...","branch":"...","file":"...","method":"...","result":"...","failure_id":"F-0NN-or-null","pr":null,"workflow":null,"evidence":"link-or-fixture"}
\`\`\`
Существующий файл исторически не полностью нормализован, поэтому **новые** записи соответствуют расширенной схеме без изменения прежних. Не записывать секреты, пользовательские макеты, email/персональные данные.

### Неудачные попытки — НЕ удалять

Даже если код не вошёл в релиз, добавить к записи:
- воспроизводимый кейс и входные параметры;
- что именно попробовали (включая номер PR, конкретный тест, expected/actual и важные числа);
- источник сообщения об ошибке, run/job URL; \`failed\`/ \`cancelled\` различать;
- почему метод не подходит и какой инвариант он нарушил;
- закрывающий коммит/откат, что из попытки полезно переиспользовать;
- новая отрицательная regression, если закономерность повторяется.

Для **новой категории ошибки** создать F-0NN в [FAILURE_REGISTER.md](FAILURE_REGISTER.md). Если старая причина повторилась — добавить dated incident к ней вместо переписывания оригинала. Для гипотез использовать слово «предположение», для воспроизведения — «подтверждено на …».

## 2. После успешного кода, перед PR

1. Обновить \`docs/history/RELEASE_CHRONICLE.md\`: версия, изменение, PR (если ещё нет — TBD), инварианты, известные ограничения.
2. Обновить \`docs/history/METHODS_AND_DECISIONS.md\` при изменении алгоритма/порядка стадий.
3. Обновить \`docs/FEATURE_MATRIX.md\`: различать \`implemented\`, \`tested\`, \`verified-on-real-input\`, \`user-confirmed\`.
4. Обновить \`HANDOFF.md\`, но **не стирать прежнюю историю**. Последний статус размещать сверху; полный архив остаётся.
5. Обновить \`docs/NEXT_CHAT_START.md\`: последний подтверждённый SHA/branch/PR/CI, точный невыполненный шаг, команды тестов, ориентиры файлов и ошибки, которых нельзя повторять.
6. Версия должна совпадать в \`Cargo.toml\`, \`Cargo.lock\`, \`package.json\`, \`package-lock.json\`, \`web/index.html\` и URL \`?v=\` используемых модулей. Кеш alpha.33 показал, что одного обновления шапки недостаточно.
7. Добавить/обновить tests. Самописные тестовые fixtures должны быть синтетическими, не содержать приватных макетов.
8. \`npm test\`/Rust/WASM/CI имеют разные статусы. Не написать «прошли» до реального вывода, а «Pages опубликовано» — до deploy success.

## 3. Порядок проверок

\`\`\`bash
npm ci
npm test
cargo test --locked
cargo build --locked --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/relief_forge.wasm web/engine.wasm
node scripts/check-wasm.mjs
npm run serve
\`\`\`

В GitHub Actions сохранять links на **job logs**. После merge отдельно проверить новый workflow для \`main\` и deploy step; PR green не означает deployed. Для runtime input vector важно дополнительно:

- EPS/Corel: проверенные \`BoundingBox\`, pt→мм, count объектов, 0-empty guard, настоящие \`C/c\`; no paints vs visible.
- PDF: страница, размер, paths/raster, plain typed XML.
- AFTER: реальное отличие geometry, количество узлов, holes, остаточные проблемы и степень coverage.
- EPS Save: \`_result\`, цвет/без цвета, нет повторного лечения, точная preview геометрия, Undo, re-import.
- Workspace: mascot, SVG rect, viewBox, opening/completed/failed, браузер пользователя по возможности.
- Performance: число объектов/точек, порог батча, память/время только измеренное; отличать догадки от метрик.

## 4. Итог сессии — обязательно

В конце **каждой содержательной разработки**:
- дополнить исторический журнал, реестр ошибок и JSONL;
- сделать Git checkpoint commit и PR, если есть изменение;
- проверить, что последний SHA реально в GitHub и доступен из следующего чата;
- обновить [NEXT_CHAT_START.md](../NEXT_CHAT_START.md), указав одну чёткую точку продолжения;
- не оставлять \`status=deployed\` при \`workflow in_progress\`/ \`failure\`/ \`cancelled\`;
- не обещать продолжение в фоне: если работа прервана, следующим шагом будет новый запрос пользователя;
- в финальном ответе указывать ссылку на файлы, PR, SHA, тесты и честные ограничения.

## 5. Состояния и подтверждения

| Статус | Что значит | Чего НЕ доказывает |
|---|---|---|
| \`source_written\` | Код есть в ветке | Что он выполняется |
| \`static_checked\` | Пройден syntax/type/unit | Работу полного импорта |
| \`native_tested\` | Реальные Rust тесты прошли | Работу браузера |
| \`wasm_tested\` | ABI/wasm проверен | Рендер на чужом компьютере |
| \`pr_ci_pass\` | Build PR завершился success | Main deploy success |
| \`merged\` | PR вошёл в main | Что Pages уже обновились |
| \`deployed\` | Main workflow build+deploy success | Что браузер пользователя перезагрузил кеш |
| \`browser_smoke\` | Конкретный браузер/input вручную проверен | Другие браузеры и железо |
| \`user_verified\` | Пользователь подтвердил свой реальный кейс | Все форматы/кейсы |

## 6. Работа с приватными файлами

Имена публичных файлов и описательные статистики можно использовать в журнале по пользовательскому разрешению, **бинарные файлы EPS/CDR/PDF из заказа, вложенные изображения и полные пользовательские SVG/логи с конфиденциальными текстами** — не коммитить. Путь \`evidence/private\` — local-only, ignored. Синтетический тест должен моделировать PostScript форму, но не воспроизводить коммерческий макет.

Проверить git diff перед commit на чувствительные данные, токены, произвольные \`sourceSvg\` и base64 EPS. В открытых отчетах избегать base64/полных document bytes.

## 7. Протокол исправления ошибочной исторической записи

Нельзя тихо менять последнюю запись, будто ошибки не было:
\`\`\`markdown
### Исправление записи (дата) — ссылки на оригинал
- В старой записи было сказано: ...
- Подтверждённые новые данные: ...
- Почему старое утверждение неверно или неполно: ...
- Новое состояние: ...
- Evidence: ...
\`\`\`
Для самого \`NEXT_CHAT_START.md\` допустимо **заменять текущие статусные поля** на новые (он по смыслу актуальный снимок). Ретроспективный журнал и failure register при этом только расширяются.

## 8. Контроль истории автоматическим тестом

Файл \`tests/history-integrity.test.mjs\` проверяет наличие и наполненность обязательных документов, актуальное соответствие версии, структуру JSONL и ссылки. Если тест падает при повышении номера релиза, **обновить документ**, а не отключать тест. Не считать «зелёным» PR, у которого история уже устарела.
